# External Beta Handoff Example

This is a checked-in example for the External Beta maintainer workflow. It
shows how three trial reports become one handoff folder with a cohort summary,
route-quality gate, and prioritized fix queue.

The example is intentionally small and redacted. It documents the artifact
shape maintainers should expect from `scripts/external-beta-cohort-report.sh`;
it is not a claim that the listed repositories are real public Beta results.

## Inputs

Each input is either a trial output directory or a `beta-summary.json` file
generated by `scripts/external-beta-trial.sh`.

| Input | Outcome | Route quality | First file |
| --- | --- | ---: | --- |
| `/tmp/codeinsight-external-beta-trial-1` | `route_hit` | `high / 96` | `src/main.ts` |
| `/tmp/codeinsight-external-beta-trial-2` | `workflow_friction` | `high / 96` | `scripts/setup.sh` |
| `/tmp/codeinsight-external-beta-trial-3` | `route_miss` | `high / 96` | `README.md` |

## Command

```bash
scripts/external-beta-cohort-report.sh \
  /tmp/codeinsight-external-beta-trial-1 \
  /tmp/codeinsight-external-beta-trial-2 \
  /tmp/codeinsight-external-beta-trial-3 \
  --output-dir /tmp/codeinsight-external-beta-handoff \
  --min-route-quality-score 70 \
  --check \
  --print-snippet
```

## Fix Queue Snapshot

| Rank | Priority | Task | First file | Recommended action |
| ---: | --- | --- | --- | --- |
| 1 | `workflow_friction` | configure MCP first call | `scripts/setup.sh` | Fix the trial workflow, docs, or issue filing path before routing changes. |
| 2 | `route_miss` | understand login routing | `README.md` | Reproduce the task, add a routing regression, then adjust selection signals. |

## Interpretation

The handoff is useful when the project has enough trial reports to discuss in
public but still needs a maintainer-owned next action. It should be attached to
an issue, discussion, or release readiness note only after redaction has been
checked in each source trial folder.

Use the queue as the immediate implementation order:

1. Fix workflow friction before route changes.
2. Keep route-quality failures out of success evidence.
3. Reproduce route misses with regression fixtures before tuning ranking.
4. Treat near misses as lower priority unless they block a common task.
